# Adaptive Teaching Planner — Frontend MVP Implementation

## Role

Act as a senior frontend engineer and software architect. You are implementing a polished, maintainable frontend MVP for an Adaptive Teaching Planner used by university teachers.

I will provide ZIP files containing UI screens generated with Stitch. These screenshots, exports, and related assets are your primary source of truth for the interface.

Your job is to inspect the supplied files, understand the intended user journeys, identify genuine missing states or screens, and implement the complete frontend in Next.js.

**Do not start coding before inspecting the supplied ZIP files. Do not invent a new UI when an existing design already covers the requirement.**

---

## 1. Product context

The product helps university teachers plan syllabus coverage, schedule teaching sessions around their actual teaching availability and institution calendar, record classroom progress, and adapt upcoming sessions when teaching does not go according to plan.

The goal of this MVP is to demonstrate a coherent, navigable, realistic product workflow. It does not need production backend infrastructure or a real AI integration.

Priorities, in order:

1. Faithfully implement the supplied UI designs.
2. Make every important user journey navigable and internally consistent.
3. Implement realistic frontend state and data flow.
4. Fill genuine gaps with the smallest reasonable UI or interaction.
5. Keep the codebase maintainable and documented.

Do not overengineer the MVP.

## 2. Start with a design audit

Before implementing anything:

1. Inspect every supplied ZIP file, screenshot, exported design, asset, and available source file.
2. Identify all unique screens, duplicate screens, alternate states, and shared components.
3. Create a screen inventory with each screen's purpose, entry point, and exit actions.
4. Map the screens to a user-flow diagram.
5. Identify missing transitions, missing states, and genuine product gaps.
6. Identify inconsistencies between the screens, such as differing labels, navigation items, or button destinations.

Create these initial documentation files:

If a required screen is missing but can be represented as a small state within an existing screen, implement it that way. Create a new screen only when the workflow genuinely requires one.

## 3. Core user journey

Implement the following workflow, adapting names and destinations to match the supplied designs.

### Authentication

Demo login → authenticated application.

### Subject setup

My Subjects → Add Subject → Subject Details → Sections & Pace → Teaching Schedule → Syllabus Upload.

The Create Subject flow may be a wizard or separate screens, depending on the supplied designs. Preserve the intended sequence.

### Planning

Syllabus Upload and Review → Pacing Matrix → Schedule Map → Teaching Plan Review → Approve Teaching Plan.

The distinction between these stages matters:

- **Pacing Matrix:** estimate and adjust teaching effort for topics and units.
- **Schedule Map:** fit topics into actual available teaching slots, respecting teaching days, times, sections, holidays, and exam periods.
- **Teaching Plan Review:** review the resulting dated sessions, identify conflicts, and approve the proposed plan.

Do not merge these stages simply because they share some information.

### Daily teaching workflow

Home or Calendar → Teaching Session → Quick Post-Class Update.

Keep the post-class interaction extremely lightweight. The teacher should be able to record whether the topic was completed, partially covered, or not covered, optionally provide a short note, and save.

Only show Plan Adjustment Preview when an update creates a meaningful proposed change. Do not force teachers through a detailed adjustment screen after every class.

### Adaptation

Post-Class Update → Optional Plan Adjustment Preview → Apply Changes or Keep Original Plan.

Show proposed changes before applying them. Preserve unaffected sessions and never silently discard topics or overwrite teacher edits.

### Existing subject workspace

Clicking a subject from My Subjects should open its existing Subject Overview. Use the subject tabs already established in the supplied designs, including:

- Overview
- Teaching Plan
- Syllabus
- Progress
- Tests & Revision
- Analytics
- Team

Do not create additional screens for every tab by default. If the supplied designs already cover the necessary information, implement those designs. If a tab has no design and is not essential to the core MVP journey, use a sensible lightweight placeholder or minimal state within the existing subject workspace.

Do not invent complex functionality merely to populate every tab.

## 4. Navigation rules

Preserve the global navigation established by the designs:

- Home
- My Subjects
- Calendar
- Notifications
- Settings

Teacher Profile should be accessible through the avatar or profile menu, not added as a permanent navigation item.

Subject-specific pages should remain within the selected subject workspace.

The global Calendar is an institution-wide view of teaching sessions and academic events. It is not a replacement for the subject-level Teaching Plan.

- Proposed sessions should not appear as confirmed events before plan approval.
- Approved sessions should appear in the global Calendar.
- Calendar events should link back to their relevant subject or session.
- Institution holidays and exam periods must be distinguishable from teaching sessions.

Keep the navigation hierarchy consistent throughout the application.

## 7. Frontend data model

Create typed models and a small mock-data layer so screens share consistent information.

At minimum, consider these entities:

- Teacher
- Subject
- Section
- SyllabusUnit
- SyllabusTopic
- TeachingSlot
- AcademicCalendarEvent
- TeachingSession
- SessionOutcome
- ScheduleChangeProposal
- Notification

Use stable IDs rather than relying on array indexes or display names as identifiers.

Relationships should be explicit. For example:

- A subject has units and topics.
- A subject may be taught to multiple sections.
- A section has a pace mode: shared initial pace or independent pace.
- A teaching session references a subject, topic, date/time, and section.
- A session outcome references the session it updates.
- A proposed schedule change references the affected sessions.

Use TypeScript types or interfaces and avoid `any` wherever practical.

Keep example data in dedicated seed/mock files, not scattered throughout JSX components.

Use realistic university examples, such as a Data Mining subject with syllabus units and topics. Clearly distinguish mock data from actual institutional data.

## 8. State management and persistence

This is a frontend prototype. Do not add a database or backend.

Choose the simplest appropriate state strategy:

- React state and context for shared application state.
- A small reducer or lightweight store if cross-screen workflows become difficult to manage.
- Browser storage for persisting demo data between refreshes when useful.

Do not introduce Redux or another state library without a clear need.

Implement the important workflow state transitions:

1. Create and edit a subject.
2. Select sections and define teaching slots.
3. Upload or enter syllabus content.
4. Review and edit extracted units and topics.
5. Adjust topic effort in the Pacing Matrix.
6. Generate a proposed schedule from available teaching slots.
7. Review and approve the plan.
8. Show approved sessions in the Calendar.
9. Record post-class outcomes.
10. Preview and apply or reject proposed schedule adjustments.

A page refresh should not unexpectedly erase an in-progress workflow if the current persistence approach can reasonably preserve it.

If data is lost or reset, make the demo behavior clear rather than silently pretending it is persisted on a server.

## 10. Simulated pacing and schedule generation

Implement a deterministic, explainable frontend planning algorithm. Do not integrate an external AI API.

The Pacing Matrix should allow teachers to adjust topic complexity, importance, and estimated teaching effort.

The Schedule Map should use:

- Confirmed syllabus topics
- Estimated teaching effort
- Selected sections and pace mode
- Teacher-defined weekly teaching slots
- The chosen planning period
- Institution holidays and blocked academic dates
- Any existing manually edited sessions

Use the available inputs to generate a proposed sequence of dated sessions.

Requirements:

- Never schedule a class on a blocked date or outside the selected teaching slots.
- Keep topics in syllabus order by default.
- Flag topics that cannot fit in the planning period.
- Flag conflicting or insufficient teaching slots.
- Show when the estimated completion date cannot be calculated.
- Do not silently omit topics.
- Preserve manual changes where possible.
- Require teacher approval before proposed sessions become confirmed calendar events.

Document the algorithm's assumptions and limitations in `docs/planning-logic.md`.

Do not present simple heuristic scheduling as sophisticated AI.

## 11. Adaptive scheduling behavior

Implement a minimal but coherent feedback loop.

After a session outcome is recorded:

- **Completed:** mark the topic or session complete. Keep the future schedule unchanged unless other evidence requires an adjustment.
- **Partially covered:** propose an additional session or remaining effort for the unfinished topic.
- **Not covered:** propose moving the topic to an appropriate available slot.

When relevant, account for section-specific progress.

A schedule adjustment must be a proposal until the teacher explicitly applies it. Provide a way to retain the original plan.

When applying a proposal:

- Update only the affected sessions.
- Preserve unrelated sessions.
- Respect holidays, teaching availability, and section assignments.
- Flag unresolved conflicts rather than silently generating an invalid plan.

The logic should be deterministic and easy to test. Do not build a complex optimization engine for the MVP.

The supplied designs are the source of truth for layout and visual style.

Study the designs before deciding on component sizes, spacing, typography, colors, borders, cards, or navigation.

Maintain a shared design system and reusable components where they are genuinely repeated, such as:

- App shell and navigation

Avoid forcing every screen into the same card-heavy layout.

The visual design should remain clean, restrained, responsive, and teacher-friendly.

In particular, daily workflows must stay lightweight:

- Post-class update should be possible in roughly 10–20 seconds.
- Use one primary question, one optional follow-up, and one save action.
- Keep notes optional and hidden until requested.
- Show adjustment controls only when meaningful changes are needed.

Do not add large dashboards, redundant metrics, unnecessary fields, or administrative reporting forms.

## 13. Real interactions and navigation

Every visible interactive control must have a meaningful behavior.

Examples:

- Buttons navigate, submit, save, confirm, or cancel as their labels indicate.
- Subject cards open the selected subject.
- Subject tabs switch to the corresponding subject content.
- Forms validate and show errors.
- Filters and selectors affect displayed data.
- Edit and delete actions update local state.
- Approving a plan changes its status and updates the Calendar.
- Rejecting a proposed change leaves the approved plan unchanged.
- Logout returns the user to the login screen.

Do not create decorative buttons that do nothing.

Use Next.js navigation correctly. Avoid full-page reloads for ordinary internal navigation.

Use appropriate form semantics, accessible labels, keyboard navigation, and clear focus states.
